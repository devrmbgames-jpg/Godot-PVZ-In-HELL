# R23 — Задачи по результатам QA основной сцены

Artifact: **SUPPORT**  
Owner task: [R23 Vertical Slice Validation](../roadmap_23_vertical_slice_validation.md)

Записано 2026-10-02 по замечаниям владельца. Все пункты ниже ожидают реализации; состояние выполнения ведётся в родительской задаче R23. Это согласованное расширение её объёма, включая новые механики трупа/мяса и подготовку ИИ.

## Актуальная карта

Владелец увеличил `content/scenes/main_level.tscn`. `DebugMarkers` по умолчанию скрыт и представляет только визуальную разметку местности. Сохранить его видимость, дочерние узлы и пользовательские изменения сцены.

Ориентиры: `ReceivingZone`, `MainDoor`, `BackDoor`, `RoomClient`, `RoomClientBathroom`, `RoomPrivate`, `RoomTraderPrivate`, `TraderClientZone`; внутри также находится `MarkerNPCSpawnPoint`. MeshInstance-разметку не превращать в коллизии или новую runtime authority. Использовать фактическую геометрию и существующие authored контракты размещения/спавна.

После изменения размеров карты предыдущие результаты проверки маршрутов не доказывают проходимость актуальной сцены. Проверить NavigationRegion, актуальность bake, проходы, вход/выход клиентов и доступ к торговцу перед новым прохождением.

## QA-01 — Управление игроком

- [ ] Устранить подскакивания при движении по ровной поверхности и тугое управление.
- [ ] Устранить задержку и нарушения плавности при резком повороте камеры.
- [ ] Проверить обычное движение, диагональ, остановку, приседание, ступени и перенос предмета; камера не должна зависеть от задержки физического шага.

Приёмка: движение и быстрый разворот устойчивы в увеличенной основной сцене. Сохранить Godot physics authority и текущие контракты ввода; причину установить до изменения параметров.

## QA-02 — Взаимодействие с торговцем

- [ ] Исправить выбор действия: доступно взаимодействие с торговцем вместо захвата его как переносимого предмета.
- [ ] Проверить доступность торговли, еды/лекарств, заказа и квеста в нормальной фазе дня.

Приёмка: обычное действие взаимодействия открывает предусмотренный интерфейс торговца; его нельзя унести как проп. Проверить приоритеты действий и authored компоненты сцены.

## QA-03 — Инвентарь сеткой

- [ ] Заменить представление инвентаря сеткой слотов с иконками.
- [ ] Использовать существующие иконки из `addons/at-icons`, предпочитать ещё не используемые в игре.
- [ ] Сохранить выбор, использование, выбрасывание, подсказки, пустые слоты и действующие ограничения инвентаря.

Приёмка: предметы различимы, действия доступны мышью и текущими способами ввода. Иконки только ссылать из проекта; содержимое addon не менять.

## QA-04 — Труп, разделка, мясо и молоток

- [ ] После смерти NPC оставить физическую заглушку трупа; остановить живой ИИ и корректно завершить его визит/челлендж.
- [ ] Сделать молоток также оружием, сохранив его существующее назначение; нож и молоток могут разделывать труп несколькими ударами.
- [ ] Число ударов и параметры оружия задать данными. После достижения порога один раз заменить труп мясом.
- [ ] Заглушка мяса: два цилиндра, изображающие мясо на кости.
- [ ] Мясо можно съесть; оно уменьшает голод через существующий контракт еды/инвентаря.

Приёмка: смерть оставляет труп; подходящие удары создают мясо ровно один раз, неподходящее действие его не дублирует; еда расходуется и меняет голод. Определить поведение трупа/мяса при Night, reset и save/load в рамках действующих lifecycle/persistence контрактов.

## QA-05 — Отладочный статус над клиентом

- [ ] Добавить читаемый отладочный статус-бар над каждым клиентом: идентификатор/номер посылки, состояние визита, здоровье, удовлетворённость и активный челлендж.
- [ ] Таймеры, условия и задачи показывать рядом с соответствующим клиентом; оставить в экранном debug HUD компактную общую сводку.
- [ ] Подключить к существующему включению отладки, обеспечить очистку при уходе/смерти/удалении клиента.

Приёмка: при нескольких клиентах понятно, чьи это данные; обычные подсказки и диалог читаются. Челлендж «от прихода до физического ухода» сохраняет прежнюю семантику.

## QA-06 — Игровые тайминги ×4

- [ ] Инвентаризировать игровые длительности и увеличить их в четыре раза, включая поиск посылки, ожидание/терпение клиента и таймеры челленджей.
- [ ] Учесть уже изменённые владельцем ресурсы: определить исходные значения и не применять множитель повторно к уже увеличенным таймингам.
- [ ] Зафиксировать перечень изменённых длительностей; значения «нет ограничения»/нулевые отключённые таймеры сохранить. Не масштабировать физический delta, расстояния, скорость или урон как таймеры.

Приёмка: конечные игровые таймеры соответствуют ×4 от согласованной исходной длительности; UI показывает действительные значения. Если отдельная длительность требует исключения, явно записать его перед приёмкой.

## QA-07 — Номер посылки сразу при входе

- [ ] Добавить authored вариант клиента, который при входе в помещение сообщает номер посылки баблом без открытия диалога.
- [ ] Использовать его для клиентов, ожидающих быстрой выдачи и не собирающихся вступать в полемику.
- [ ] Сообщение выдаётся один раз за визит после определения действительного номера; такой клиент может получить посылку без обязательного диалога.

Приёмка: виден правильный номер, повторный вход/обновление состояния не спамит баблами; обычные диалоговые и опасные клиенты сохраняют свои правила.

## QA-08 — Клиент сам начинает диалог

- [ ] Добавить authored вариант клиента, который инициирует диалог при первом подходе игрока.
- [ ] Задать дистанцию данными, запускать один раз за визит, учитывать занятый диалог/модальное действие и состояние клиента.

Приёмка: выбранный клиент начинает разговор без клика; закрытие диалога или повторный подход не запускает его снова. Обычный клиент по-прежнему ждёт взаимодействия; быстрый клиент QA-07 не получает обязательный разговор.

## QA-09 — Анимация ножа

- [ ] Добавить простейшую анимацию удара ножом через `AnimationPlayer`.
- [ ] Связать запуск и момент удара с действующей механикой атаки, корректно прерывать при смене предмета/смерти.

Приёмка: взмах виден, попадание не применяется дважды, нож подходит для QA-04.

## QA-10 — Вращаемые кнопки/вентили

- [ ] Поддержать вращение этого типа интерактивных объектов с authored осью и диапазоном угла.
- [ ] В thin Entity glue предоставить типизированный сигнал `progress_changed(progress: float)`; предложенный контракт — нормализованный прогресс `0..1`.
- [ ] Эмитировать изменение действительного прогресса, включая reset/restore; определить начальное значение и подключение к кнопке/двери без дублирования действия завершения.

Приёмка: вентиль вращается, подписчик получает актуальный прогресс и может управлять другим объектом. Переиспользовать существующее prolonged interaction; отдельную System ради этого сигнала не создавать.

## QA-11 — NPC обходят друг друга

- [ ] Сохранить `NavigationAgent3D` у NPC и настроить взаимный обход в узких проходах и очередях.
- [ ] Согласовать avoidance velocity с действующим физическим контроллером NPC; не телепортировать тела и не создавать вторую authority движения.

Приёмка: несколько клиентов обходят друг друга и доходят до цели без постоянного выталкивания и застревания. Проверить на актуальной увеличенной карте с настоящими коллизиями.

## QA-12 — Заготовка полноценного ИИ

- [ ] Выделить простой контракт выбора намерения/действия, пригодный для будущего адаптера LimboAI.
- [ ] Сохранить NavigationAgent, текущие сценарии визита и отдельные способности: до трёх ближних и трёх дальних атак с привязкой к анимациям.
- [ ] Предусмотреть выбор выгодной доступной способности по ситуации через данные/контракт, без сложного нового фреймворка.

Приёмка: существующий ИИ продолжает работать через понятный шов для будущего поведения. Установка LimboAI и полноценное дерево поведения в этот пункт не входят; Components остаются данными, Systems не вызывают друг друга как сервисы.

## QA-13 — Редактируемые материалы выделения и контракт overlay

- [ ] Вынести материалы выделения во внешние файлы ресурсов `.res`, которые владелец может менять в редакторе без правки кода.
- [ ] Создать несколько отдельных материалов по состояниям: как минимум «доступно» и «недоступно» (например, предмет слишком тяжёлый). Предусмотреть замену материалов и добавление других состояний через authored настройки.
- [ ] Выбирать материал по действительной доступности взаимодействия; базовый материал объекта сохранять.
- [ ] Зафиксировать и соблюдать общий игровой контракт: `MeshInstance3D.material_overlay` всегда предназначен для интерактивной обратной связи и выделений. Остальные визуальные эффекты не должны занимать этот слот.
- [ ] Проверить существующие назначения overlay и корректную смену/очистку интерактивного выделения при смене цели, потере доступности, закрытии интерфейса и удалении объекта. Несколько источников интерактивной обратной связи не должны перезаписывать друг друга произвольно.

Приёмка: внешние `.res` доступны для редактирования и замены; доступный и недоступный объект используют соответствующие материалы. Изменение ресурса меняет выделение в игре без изменения скриптов; базовый материал сохраняется, зависшего выделения нет. Контракт `material_overlay` действует для всего проекта.

## Порядок и проверка

Сначала актуальная карта, управление и торговец (QA-01/02/11), затем тайминги, читабельность и выделение (QA-05/06/13), инвентарь/оружие/труп/еда (QA-03/04/09), поведение клиентов (QA-07/08), glue и заготовка ИИ (QA-10/12). Каждый пункт закрывать отдельно по фактическому результату.

Команды проверки расширяются в [Developer Console Testing](../developer_console_testing.md); это вспомогательное воспроизведение, не доказательство прохождения дня без debug. Выполнить узкую проверку изменяемых контрактов, интеграционную проверку близко к завершению и передать основную сцену владельцу для повторного игрового QA согласно его просьбе.
