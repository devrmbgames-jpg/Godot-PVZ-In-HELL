# Живые жители Ада / 01 — основа личности и контракты

Status: **PLANNED**

Created: 2026-10-15. Updated: 2026-10-16. Parent: [общая задача](../npc_living_society.md). Первый этап; затем [02 — потребности и выбор целей](02_needs_and_utility.md).

## Task state

### Goal

Закрепить единственных владельцев личности, потребностей, отношений, навыков, целей и ресурсов; согласовать новую симуляцию с текущими ТЗ и подготовить минимальные типизированные контракты первого прототипа.

### Constraints / acceptance

- Общие решения и статус принадлежат корневой задаче. Этот этап не подменяет реализацию существующих ТЗ и не объявляет их завершёнными.
- Постоянный ID личности не зависит от архетипа, заказа, тела, имени, seed или порядка ресурсов; авторские жители не генерируются повторно.
- GECS Components/Relationships и вложенные записи имеют одну власть над состоянием; definitions неизменяемы, Blackboard/UI/ctx — адаптеры.
- Существующий голод, деньги, вещи, календарные обязательства и физическое движение не получают второго владельца.
- Новая кампания; старые сохранения не мигрируют и не перезаписываются.

### Current

Карта текущей основы и исследовательские выводы перенесены из согласованного плана. Код, сериализация и контракты не изменены. Рабочая таблица ниже описывает целевые границы, а не наличие всех новых типов.

### Next

От названных владельцев уточнить актуальные типы и пути, согласовать зависимости с ТЗ постоянных жителей, подготовить карточки Карги, Дьявола и Скромника и минимальный контракт состояния/сохранения по [GDD](../../../docs/game_design/npc_needs_and_intrigue_gdd.md). Не создавать неиспользуемые будущие framework API.

### Validation

Документные проверки (2026-10-16): **PASS** — UTF-8, ссылки, разделы/статусы, полнота GDD, порядок зависимостей, сохранение торговых/диалоговых контрактов, предел 200 строк и Git whitespace checks. Игровая реализация, Godot parser, GUT, headless smoke и gameplay/visual QA новой системы: **NOT_RUN**. Параметры требуют проверки прототипом; документация не доказывает runtime-приёмку.

### Owner QA / blockers

Новая кампания и отсутствие миграции утверждены. Имена, личные сюжеты и неподтверждённые предложения прежних ТЗ ещё требуют авторского наполнения; не придумывать окончательный канон. Новые типы получают конкретные имена при реализации в существующих доменах, с обновлением их единственного контракта.

## Определения и интерфейсы

- Ввести минимальные типизированные определения потребности, цели и рецепта. Они задают настройки, условия и ожидаемые результаты; runtime-состояние находится отдельно.
- Определение потребности задаёт применимость, изменение и кривую срочности; определения цели связывают оценку с конкретным поддеревом/действием; рецепт — реальные входы, выход и завершение.
- Типизированные запросы/результаты нужны для социальной встречи, работы, снабжения и посреднического поручения; определения рациона задают подходящую еду и предпочтения обстановки. Различать запрос, принятие/ожидание, отказ, отмену и подтверждённое завершение.
- Оценка — чистое чтение доступного контекста; новые clocks и recurring work принадлежат Systems, дискретные изменения — Observers/операциям, LimboAI — порядок исполнения.
- Контракт длительного действия содержит устойчивую идентичность, результат и отмену с освобождением собственных резервов; прежний callback не отменяет заменившую его работу.
- Не заводить универсальную state-machine в BT leaf, generic service-dispatcher, свой BT runtime или planner на будущее.

## Состав и минимальное наполнение

- По [GDD](../../../docs/game_design/npc_needs_and_intrigue_gdd.md) девять постоянных жителей имеют девять авторских домашних мест; Вампир переводится в постоянный состав, Потерянный остаётся знакомым возвращающимся гостем.
- Реальные средства, запасы примерно на два дня и входы первой партии задаются один раз новой кампанией. Круг: Дьявол → Элементаль → Бугай → Скромник → Охотник → Карга → потребление/восстановление.
- Бюджеты/поручения, знания, разрешения и стартовые запасы должны иметь одного владельца до расширения прототипа. Внешняя замена сырья медленнее/дороже, гость не единственный обязательный путь.

## Сохранение и жизненный цикл

- Расширить явные `SAVE_FIELDS`/codec/snapshot validation только для реального долговременного состояния. Новая игра получает утверждённые авторские defaults, а не случайный повтор личности.
- Версионировать схему. Старая схема распознаётся до применения и записи; понятный отказ оставляет файл неизменным. Не вводить постоянный старый runtime ради совместимости.
- Не сохранять live Node/Entity/RID/instance ID как долговременную личность, сырые маршруты, derived utility scores или Blackboard-копию.
- HOME в физической комнате требует явной миграции нынешнего dormant-контракта через placement owner: живой хозяин сохраняет тело, физику и реакции; OUTSIDE/DEAD остаются dormant. Камера не управляет участием, работа завершается однократно без offline progress/dormant catchup; подробности в ТЗ домов.
- Сохранять ID Потерянного между визитами; после смерти следующий визит по расписанию не раньше `death_day + 2`, без районного дома. Жителям сохранять reset физических состояний и финансовые обязательства по ТЗ заселения; добыча каждой смерти имеет ключ личности/номера смерти.

## Проверяемая приёмка

- [ ] F1: каждый новый изменяемый показатель имеет один документированный owner/writer и один путь сериализации.
- [ ] F2: постоянные ID, дома и роли сохраняют контракт; shared definitions не мутируют при жизни конкретного NPC.
- [ ] F3: hunger/inventory/commerce/calendar/physics продолжают использовать существующих владельцев.
- [ ] F4: минимальные типы используются прототипом; нет пустых API GOAP и параллельного scheduler.
- [ ] F5: новая схема проходит round-trip; старая отклоняется до изменения файла, без неявной миграции.
- [ ] F6: зависимости существующих задач названы и открытые gates не объявлены выполненными.
- [ ] F7: девять домашних мест, постоянный Вампир и сохраняемая личность Потерянного согласованы; бюджеты/поручения/знания/разрешения не имеют второй власти.
