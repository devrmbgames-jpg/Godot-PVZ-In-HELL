## Task state

### Goal

Подтвердить многодневное продолжение одной истории жителей: реальные ресурсы, причинные отношения, устойчивое исполнение, сохранение, смерть/возвращение и справедливые бюджеты на расчётном населении.

### Constraints / acceptance

- Headless функциональная проверка не доказывает визуальное качество и читаемость поведения.
- Нет PASS без фактически выполненного check; обязательные parser/runtime/review/owner gates не снимаются отсутствием инструмента или отдельной QA-карточкой.
- Старые сохранения не мигрируют; файл сохраняется при понятном отказе несовместимой схемы.
- Не добавлять unrelated исправления/новых NPC и не менять третьесторонние аддоны ради приёмки.
- Общий статус принадлежит корневой задаче; здесь фиксируются итоговые проверки, риски и открытые findings этого этапа.

### Current

Сохранён план проверок будущей реализации. Новая система не реализована; фактических замеров, parser/GUT/smoke и визуальной проверки её поведения нет.

### Next

После 05 выполнить профильные технические gates на согласованном implementation checkpoint, измерить одинаковый базовый/новый сценарий, собрать read-only review и провести разрешённую ручную приёмку. В корне обновить общий результат только по фактической evidence.

### Validation

Документные проверки (2026-10-16): **PASS** — UTF-8, ссылки, разделы/статусы, полнота GDD, порядок зависимостей, сохранение торговых/диалоговых контрактов, предел 200 строк и Git whitespace checks. Игровая реализация, Godot parser, GUT, headless smoke и gameplay/visual QA новой системы: **NOT_RUN**. Параметры требуют проверки прототипом; документация не доказывает runtime-приёмку.

### Owner QA / blockers

Рендерный запуск/визуальная QA требуют отдельного разрешения владельца. Без подтверждённой читаемости не закрывать соответствующие критерии. Каталоги/эффекты и авторские карточки должны быть закончены у владельцев; названия и placeholders не доказывают готовность.

## Матрица функциональной приёмки

| Группа | Обязательные сценарии |
| --- | --- |
| Мотивы и характер | Одинаковый голод — разные допустимые решения; навык отдельно от интереса; выключенная потребность не создаёт дефицит; несколько мотивов одного реального дела. |
| Устойчивость | Близкие оценки не вызывают метание; существенный факт меняет цель; emergency прерывает; RUNNING работа не перезапускается каждым BT tick. |
| Социальные связи | Асимметрия A → B / B → A; уважение/страх отдельно от симпатии; помощь/обман/вред влияют на новую встречу. |
| Знания | Факт/подозрение/неизвестное различаются; свидетели получают доступные сведения; скрытые координаты/виновник не раскрываются. |
| Социальная встреча | Согласие, отказ, занятость, уход, смерть/удаление участника; нет бесконечного удержания собеседника и чужого intent cleanup. |
| Снабжение | Один активный запрос, бюджет/комиссия, прямой и посреднический путь, отказ исполнителя/игрока, внешняя замена; один посредник не делегирует дальше. |
| Ресурсы/работа | Два претендента на один слот/ингредиент; входы и выходы атомарны; отказ/отмена не дают товар/опыт; нет двойной оплаты. |
| Поиск/отмена | Недостижимая/удалённая/заменённая цель, потеря рабочего места, stale token/receipt, timeout; конечная попытка и освобождение собственного резерва. |
| Дом/календарь | STREET и живой HOME в физической комнате доступны вне камеры; домашняя работа завершается однократно; пауза/закрытое приложение не дают прогресс, dormant BT не догоняет пропущенное. |
| Личное пространство | Девять комнат-подсцен с дверью/кроватью/Area3D; запирание, конечная высокая прочность, приглашённые игрок/NPC, обнаруженный чужак/отзыв/уход, отсутствие всеведения, блокировка прохода без телепорта; состояния переживают save/load. |
| Возвращение | День №1 → отсутствие №2 → возврат №3; повтор утра не дублирует тело/результат; та же личность, память, отношения, навыки и финансовые обязательства. |
| Сохранение | Round-trip до/после запроса, резерва, работы, выпуска, продажи, социального эффекта и смерти; никаких raw live-ссылок и повторного применения событий. |
| Совместимость | Автовыдача/получатель/посылка, торговые фазы/цены/лимиты, независимые терминалы, самооборона, плата кровью и особые механики сохраняют контракт. |
| Сценарии/ритм | Запрещённое вмешательство не выбирается, разрешённое ведёт в авторскую ветку; нет иммунитета или двойной награды; лимиты старта переживают save/load. |
| Интриги/знания | Шесть шаблонов конечны; продавец не читает скрытого заказчика; ложное обвинение/подложенная вещь не переписывают фактическое авторство. |
| Состав/рацион | Девять домов, постоянный Вампир, один Потерянный между визитами; особые рационы, новизна занятий и добыча каждой смерти без бесплатных дублей. |

Проверять существующие baseline-сценарии перед объявлением независимого дефекта регрессией новой серии. В завершённом объявленном объёме не оставлять старый и новый выбор поведения одновременно.

## Многодневный headless сценарий

1. Новая кампания и **семидневный** сценарий по [GDD](../../../docs/game_design/npc_needs_and_intrigue_gdd.md): исходный запас примерно на два дня/первую партию, прототип Карга–Дьявол–Скромник, затем Бугай/Элементаль и весь состав.
2. Карге не хватает ингредиента: один запрос → реальная поставка → резерв → работа → продукт; проверить паузу и save/load на переходах.
3. Один продукт расходуется на еду, другой продаётся в допустимой фазе. Подвох имеет настоящий эффект; обнаружение меняет доверие один раз.
4. Второй NPC претендует на ресурс/место; затем опасность прерывает действие и встречу без двойного расхода и зависшего резерва.
5. Смерть в день №1 и возврат №3 продолжают ту же историю. Повтор подготовки утра/save-load не создаёт награду/товар/пополнение.
6. В последующих встречах отношения и доступные знания влияют на решение; скрывшаяся цель не получает бесконечную погоню.
7. Доказать полный производственный круг на девяти жителях и возвращающемся Потерянном, затем на диагностической конфигурации **30 NPC**. Игрок игнорирует необязательные просьбы, NPC находят альтернативы; ни одна основная цепочка не зависит только от гостя.

За семь дней проверить запланированные интриги, прекращение/восстановление после смерти поставщика и следующий допустимый визит Потерянного не раньше `death_day + 2`. Параллельно пройти запрещённое/разрешённое вмешательство в отказ и сценарную доставку; стадии, награды и слоты не повторяются. Техническая NIGHT не становится интерактивным окном.

## Бюджеты и производительность

- Сохранить `S_NpcCadence`, справедливое обслуживание due actors, coalesced wakes и отдельный route budget.
- На одинаковой конфигурации до/после измерить CPU decision/perception/routing, максимальное ожидание решения и число deferred работ; приложить условия и результаты, не обещать FPS без замера.
- На 30 NPC burst событий не превышает authored work-unit cap; каждый допустимый участник получает обработку в конечной границе согласно scheduler contract.
- Нет нового полного world/scene scan в каждом AI tick, покадровой загрузки ресурсов, неограниченной очереди одинаковых запросов или перезапуска RUNNING работ.
- Не расширять ради приёмки исследование shutdown-only retention Godot 4.7.1. Известная engine limitation — DEFERRED по политике; реальный gameplay growth/живые утечки/ошибки lifetime требуют исправления.

## Порядок технических gates

1. После согласованного набора изменений проверить formatter изменённого GDScript: `python utils/check_gdscript_format.py --changed` либо подходящий `--base` для уже закоммиченного этапа.
2. Выполнить настоящий Godot parser через `utils/godot_agent.ps1 -Action ParseChanged` или `-Action ParseFiles -Paths ...`; отсутствие MCP не отменяет CLI.
3. Для существенного этапа: `python utils/validate_agent_changes.py`, `python -B utils/validate_architecture.py --strict`, `python utils/validate_project_structure.py` и затронутые validators ресурсов/диалогов.
4. Focused GUT через `utils/godot_agent.ps1 -Action GUT -TestPath res://tests/gut/<focused_test>.gd`; выбрать реальные тесты hunger/community/perception/intent/scheduling/decision-budget/smart-objects/dialogue/snapshot и новые правила по фактическому diff.
5. Соответствующий bounded smoke через `utils/run_smoke.ps1 -Name <focused_smoke>`; новый интеграционный сценарий должен реально запускаться headless, без рендерного gameplay.
6. На существенных закоммиченных этапах [review-orchestration](../../skills/review-orchestration/SKILL.md): Main — единственный writer/менеджер, reviewer читает immutable full SHA, принятые P0/P1/P2 закрываются до DONE.

Использовать [validation-workflow](../../skills/validation-workflow/SKILL.md) и [GUT](../../skills/gut-testing/SKILL.md). Выбирать узкую достаточную поверхность; не запускать все тесты после каждой мелкой правки и не выдавать static check за engine check.

## Ручная приёмка после разрешения

- Игрок различает жителей по привычкам и может объяснить, почему один попросил еду, другой ушёл, третий занялся ремеслом.
- Игрок замечает нехватку/результат работы и понимает роль ПВЗ в снабжении без просмотра внутренних scores.
- Помощь, обман, отказ и возвращение имеют заметное продолжение; реакция соответствует известным сведениям и характеру.
- Отсутствует ощущение непрерывной случайной агрессии, постоянных отвлечений и всеобщего знания скрытых действий.
- Специальные сцены обслуживания остаются выполнимыми; обычный интерфейс не раскрывает отладочную истину.

Для каждого вопроса фиксировать наблюдавшийся результат и ошибки понимания, а не только факт запуска. Если разрешения/ручной приёмки нет, статус gate — **NOT_RUN / OWNER_QA**, а не PASS.
