# ТЗ 05 — Сканер, терминал, маркер и полки

## Цель

Создать информационный workflow приемки.

## Scanner

Scanner — физический предмет.

При наведении на незарегистрированную Package и использовании Scanner через action руки:

1. звучит beep;
2. Package получает регистрационный номер;
3. Package переходит в Registered;
4. Terminal получает запись;
5. на Terminal отображается номер, краткое содержимое и optional comment.

По умолчанию предмет в правой руке используется LMB, в левой — RMB; `swap_hand_controls` из RM06.1 меняет mapping. Scanner не должен быть жестко привязан к физической правой руке.

Повторный scan не создает новый номер.

## Нумерация посылок — обязательный контракт

Регистрационный номер Package — это **короткий складской номер**, а не номер дня/цикла.

### Формат

Базовое отображение:

```text
№001
№002
№003
...
```

Правила:

- базовый номер хранится как положительное целое число;
- в UI/на наклейке он отображается с ведущими нулями минимум до трех цифр: `№001`, `№002`, ...;
- номер **не содержит day/cycle prefix**;
- схема вида `DDD-NNN` запрещена;
- смена дня сама по себе номер не меняет и не освобождает.

### Allocation / reuse

При регистрации новой Package allocator обязан выдать **минимальный свободный положительный номер** среди номеров, которые прямо сейчас заняты активными/невыданными Package.

Package сохраняет номер столько дней, сколько она остается в обороте. Клиент может забрать её в день поступления или через несколько дней.

Номер освобождается только когда соответствующая Package реально завершила складской lifecycle: например, была выдана клиенту и больше не считается активной Package склада. После освобождения номер возвращается в пул и должен быть переиспользован раньше новых больших номеров.

Пример:

```text
День 1:
пришли 5 Package
→ №001, №002, №003, №004, №005

Клиенты забрали:
→ №001, №003, №004

Остались заняты:
→ №002, №005

День 2:
пришли еще 6 Package
→ №001, №003, №004, №006, №007, №008
```

То есть allocator каждый раз ищет свободные номера снизу вверх, а не продолжает бесконечно увеличивать sequence и не сбрасывает sequence по дням.

Это намеренное gameplay-правило: игрок должен иметь возможность организовать физическое хранение по стабильным диапазонам, например:

- первая полка: №001–№010;
- вторая полка: №011–№020;
- следующая: №021–№030.

### Будущие суффиксы

Позже отображаемый номер может получить suffix/marker, обозначающий свойства Package: fragile, oversized и т.п.

Suffix:

- является отдельными presentation/metadata данными;
- не участвует в allocation;
- не делает базовый номер занятым дважды;
- не меняет числовой порядок и правила reuse;
- не должен встраиваться в allocator key.

То есть сортировка и reuse всегда определяются базовым числом `001`, `002`, `003` и т.д., независимо от будущего suffix.

## Terminal

Показывает список зарегистрированных посылок текущего цикла.

Для каждой:

- номер;
- краткое содержание;
- комментарий;
- status;
- при необходимости предупреждающие tags.

Terminal не показывает автоматически, на какой физической Shelf лежит коробка.

## Marker

Marker — физический инструмент.

При удержании Marker:

- use-action той руки, в которой находится Marker, включает режим рисования;
- при стандартном mapping это LMB в правой руке и RMB в левой;
- `swap_hand_controls` меняет mapping;
- движение мыши оставляет линии на поверхности коробки.

Для прототипа достаточно свободного рисования. Распознавание текста не требуется.

Marker используется как mnemonic tool самого игрока.

## Shelf

В помещении находятся физически пронумерованные Shelf/ячейки.

Игрок сам решает:

- переписать номер на коробку;
- использовать номер Shelf;
- запомнить расположение;
- придумать собственную систему.

## Будущий upgrade

Предусмотреть данные для `LabelPrinter`, который позже сможет автоматически создавать наклейку после scan.

Полная реализация принтера не обязательна для первого vertical slice.

## Критерий готовности

Игрок сканирует Package, видит запись на Terminal, берет Marker, наносит собственную метку и кладет коробку на выбранную Shelf.
