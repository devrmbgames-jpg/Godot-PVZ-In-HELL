# ТЗ 08.1 — Расстановка, продолжительные взаимодействия и физические слоты

## Позиция в roadmap

Implementation task: [R11.1 — Extended Interaction / Arrangement](../../agent_tasks/roadmap_11_1_extended_interactions_and_arrangement.md).

Выполнить после базового interaction/hand/carry contract RM06.1 и до R12 Dialogue integration. Это design-ТЗ 08.1; номер `08.1` не является implementation ID.

Это ТЗ добавляет общие world-interaction механики, которые затем должны переиспользоваться дверями, мебелью, инструментами, хранением и будущими puzzle/challenge сценариями.

## Цель

Дать игроку возможность не только брать и использовать предметы, но и:

- выполнять действия, требующие удержания interaction некоторое время;
- открывать, закрывать и отпирать физические объекты;
- хранить небольшие предметы в видимых физических слотах;
- аккуратно укладывать Carry-объекты в authored placement-зоны;
- самостоятельно расставлять и фиксировать мебель/предметы в мире.

Не создавать отдельную ad-hoc interaction-систему под каждый конкретный объект. Новые механики должны расширять существующий targeting/action/prompt contract.

## Продолжительное взаимодействие

Нужен общий тип interaction, который завершается не сразу, а после удержания действия в течение заданного времени.

Примеры:

- игрок закручивает вентиль;
- стучит молотком;
- удерживает кнопку;
- снимает фиксацию мебели;
- выполняет другое действие, которое визуально и логически занимает время.

### Базовый contract

Продолжительное взаимодействие является тем же contextual `InteractionAction`, но имеет duration.

По умолчанию:

- duration = **1.5 секунды**;
- duration должна быть data-driven и переопределяться для конкретного action;
- обычный `execute/complete` считается успешным только после заполнения progress до 100%;
- отпускание кнопки до завершения не должно ошибочно вызывать обычный мгновенный `interact`;
- один input не может одновременно завершить prolonged action и пройти в другое действие более низкого приоритета.

Нужен runtime progress, принадлежащий gameplay state/action, а не UI.

UI только отображает состояние:

- под прицелом показывается небольшая progress bar;
- шкала видна во время активного prolonged interaction;
- при повторном наведении retained progress должен отображаться корректно;
- UI не является authority и не решает, завершено ли действие.

### Reset policy

Для каждого prolonged action задается один из режимов:

| Режим | Поведение при прекращении взаимодействия |
| --- | --- |
| `DECAY` / Постепенно | progress постепенно уменьшается с data-driven скоростью, пока игрок не взаимодействует |
| `INSTANT` / Мгновенно | progress сразу становится 0 |
| `ON_COMPLETE` / По завершению | незавершенный progress сохраняется; reset в 0 происходит только после успешного заполнения до 100%, поэтому action можно выполнить снова |
| `NEVER` / Никогда | progress сохраняется навсегда; после достижения 100% action считается завершенным одноразовым trigger и повторно сам не сбрасывается |

Для `DECAY` скорость потери progress должна задаваться данными отдельно от duration.

Потеря focus, отпускание input или временная невозможность продолжить действие должны использовать тот же reset policy. Удаление/disable target должно безопасно очищать runtime participation без вызова completion.

### Completion semantics

Completion должен быть атомарным:

1. action проверяет, что actor/target всё ещё валидны;
2. progress достигает 100%;
3. gameplay effect выполняется ровно один раз;
4. затем применяется post-completion policy.

Если target перестал быть валиден непосредственно перед completion, gameplay effect не выполняется.

## Двери и замки

Door использует общий interaction framework.

Минимальные состояния:

- `OPEN`;
- `CLOSED`;
- `LOCKED`;
- `UNLOCKED`.

Поведение через `E`:

- закрытая и незапертая дверь → `[E] Открыть`;
- открытая дверь → `[E] Закрыть`;
- закрытая запертая дверь при наличии подходящего предмета → `[E] Отпереть`;
- запертая дверь без подходящего предмета не должна выдавать ложный prompt успешного действия.

Разблокировка и открытие — разные gameplay transitions. Одно нажатие, которое только что отперло дверь, не обязано одновременно открыть её; после unlock prompt становится `[E] Открыть`.

### Access requirement

Замок не должен зависеть от конкретного класса `Key`.

Requirement должен уметь проверять как минимум:

- точный стабильный item ID;
- одну или несколько metadata/tag характеристик.

Это позволит использовать ключи, карты доступа, инструменты и будущие quest items через один contract.

Источник доступного предмета не должен быть hard-coded только в одну руку: проверка должна работать через общий item-access contract и в будущем учитывать hand slots, physical storage slots и другие разрешенные источники.

Расходуется ли предмет при unlock — отдельная data-driven опция.

## Выдвижные ящики

Drawer использует тот же общий open/close state contract, что и Door, но вместо вращения перемещается между authored transforms/limits.

Требования:

- `[E] Открыть` / `[E] Закрыть`;
- движение ограничено допустимым ходом;
- объект не должен телепортироваться сквозь физическое препятствие;
- текущее состояние доступно gameplay/challenge logic;
- конкретная геометрия движения не должна быть зашита в общий interaction resolver.

Door, Window и Drawer должны различаться presentation/kinematics, а не иметь три независимые системы prompts/state transitions.

## Physical Storage Slots

Нужна отдельная переиспользуемая механика физических слотов для небольших предметов.

Она **не связана напрямую** с `LEFT_HAND`, `RIGHT_HAND` или `CARRY` и не заменяет их.

Она также отличается от виртуального stack/quantity Inventory из [ТЗ 12](12_inventory_and_consumables.md): physical slot хранит конкретный физический Entity в мире.

### Игрок

На Player находится `N` authored physical slots.

Игрок может:

1. опустить камеру и посмотреть на своё тело;
2. навести прицел непосредственно на нужный интерактивный slot;
3. положить предмет из руки в slot;
4. забрать предмет из slot обратно в руку.

Сами slots предпочтительно реализовать как отдельные Entity/interaction targets с собственным anchor и occupancy state.

Такой contract должен позволять позже использовать те же slots для:

- upgrade, увеличивающего число слотов на Player;
- пояса/разгрузки;
- настенных держателей;
- стеллажей;
- полок для мелких предметов;
- tool racks.

Не создавать специальную Player-only inventory реализацию, если ту же задачу решает общий physical slot.

### Transfer

Physical slot хранит максимум один совместимый Entity, если его capacity явно не расширена будущими данными.

Slot может иметь data-driven filter:

- допустимый item ID;
- tag/category;
- размер/type;
- unrestricted.

`E/F` должны использовать тот же primary/secondary hand mapping, который определен hand-system:

- пустой slot + подходящий предмет в выбранной руке → transfer hand → slot;
- занятый slot + доступная выбранная рука → transfer slot → hand;
- если целевая рука занята, replacement выполняется только через общий hand replacement contract, а не скрытым удалением предмета;
- операция сначала валидируется целиком и только затем меняет ownership/slot relationships.

Предмет в physical slot остается конкретным Entity, а не превращается в quantity/value.

## Аккуратное складывание Carry-объектов

Нужны authored `PlacementSlot` / `PlacementArea`, помогающие игроку аккуратно размещать крупные Carry-объекты.

Это **assist-механика**, а не жесткое владение объектом.

### Поведение

Если Player:

- держит совместимый `CARRY` объект;
- подходит достаточно близко к свободной placement area;
- area может принять этот тип объекта;

то:

- подсвечивается точка/зона установки;
- появляется prompt `[E] Сложить`;
- по нажатию игра пытается аккуратно разместить Carry-объект в authored target transform.

Перед commit placement нужно повторно проверить:

- area всё ещё свободна;
- объект совместим;
- целевой transform не создаёт недопустимое пересечение.

Если validation не прошла, placement не выполняется и Carry ownership не теряется.

При успешном placement:

- Carry relationship освобождается;
- объект один раз выравнивается по authored placement transform;
- объект остается обычным физическим объектом мира после размещения;
- slot/area не должна автоматически делать его `freeze` или запрещать Grab, если это отдельно не настроено другой механикой.

### Occupancy

Occupancy должна определяться фактическим присутствием подходящего объекта в area, а не вечным логическим claim.

Если area занята:

- она не предлагает `[E] Сложить`;
- не перехватывает interaction;
- Player всё ещё может физически вытолкнуть находящийся там объект;
- Player может попытаться вручную впихнуть другой объект обычной физикой;
- когда объект покинул area, slot снова становится доступным.

Placement slots нужны как удобство для полок и аккуратной организации, но не должны превращать физический мир в grid inventory.

## Фиксация мебели и объектов

Игрок должен иметь возможность самостоятельно расставлять мебель и другие подходящие физические объекты, а затем фиксировать их в выбранном месте.

Основной инструмент — `Hammer`.

### Зафиксировать

При Hammer в активной руке LMB выполняет `Fix/Anchor` над подходящим target.

Перед фиксацией объект должен:

- поддерживать anchoring;
- не находиться в `CARRY`, hand slot, Push или другом held/control state;
- находиться неподвижно заданное время;
- иметь linear/angular velocity ниже data-driven thresholds.

Требуемое время покоя и velocity thresholds должны быть configurable.

После успешного Fix:

- объект помечается как `anchored_by_player`;
- для `RigidBody3D` включается `freeze = true`;
- Grab для этого объекта временно отключается;
- сохраняются исходные свойства, которые необходимо восстановить при Unfix.

Не считать любой изначально Static/frozen объект «зафиксированным игроком». Нужен отдельный runtime state, чтобы не размораживать authored world geometry.

### Снять фиксацию

При Hammer в руке удержание `F` на объекте, зафиксированном Player, запускает prolonged interaction.

По умолчанию используется duration prolonged interaction, если объект/инструмент не переопределяет его.

После успешного completion:

- снимается `anchored_by_player`;
- восстанавливается исходное состояние Grab;
- восстанавливается базовое physics/freeze property объекта;
- объект снова становится доступным обычной физике.

Если prolonged interaction прерван, применяется configured reset policy этого action.

### Защита от «летающей мебели»

При снятии фиксации выполнить **одноразовую** проверку соседей/опирающихся объектов.

Нужна configurable tolerance, по умолчанию ориентировочно **0.05 м**.

Если рядом/сверху находятся другие объекты, которые:

- тоже были зафиксированы Player;
- физически опираются на освобождаемый объект или находятся в пределах support tolerance таким образом, что после его освобождения остались бы висеть;

они также должны быть включены в операцию unfix.

Проверка выполняется в момент unfix, а не каждый physics frame.

Если возникает цепочка зафиксированных объектов друг над другом, допустимо собрать весь зависимый support cluster в рамках этой одной операции и снять фиксацию у него целиком.

Нельзя автоматически размораживать authored StaticBody/world geometry или чужие неподходящие объекты только потому, что они находятся рядом.

## Общий принцип ownership и interaction

Новые механики должны использовать уже существующие targeting/action/control-focus правила.

Приоритеты:

- prolonged interaction владеет своим input до cancel/complete;
- modal/control-capturing interaction не пропускает тот же input в hand/carry actions;
- physical slot transfer не создает второго owner;
- placement сначала валидируется, потом освобождает Carry;
- anchoring не заменяет physics ownership и не телепортирует объект постоянно.

Runtime state должен находиться в Components/Relationships/Systems, UI только отображает его.

## Критерии готовности

- Есть reusable prolonged interaction с duration 1.5 s по умолчанию и четырьмя reset policies: decay, instant, on-complete, never.
- Progress bar под прицелом отображает реальный gameplay progress и не является authority.
- Door открывается/закрывается и может быть отперта предметом по ID или metadata/tag.
- Drawer использует тот же state contract, но физически выдвигается/задвигается.
- Player имеет несколько видимых physical item slots; конкретный предмет можно переложить hand ↔ slot через обычный interaction.
- Та же slot-механика пригодна для будущих полок/tool racks и не зашита в Player.
- Свободная placement area предлагает `[E] Сложить`, безопасно выравнивает Carry-объект и после placement не запирает его в слоте.
- Занятая placement area не перехватывает interaction и освобождается автоматически после физического удаления объекта.
- Hammer фиксирует неподвижный допустимый объект; `freeze` и Grab state меняются только после validation.
- Hold `F` с Hammer выполняет prolonged Unfix и восстанавливает исходные свойства.
- Unfix делает одноразовую support-neighbor проверку и снимает фиксацию с зависимых player-anchored объектов, чтобы не оставлять «летающую» мебель.
- Игрок может самостоятельно переставлять, организовывать и фиксировать мебель без обязательного строительного режима или grid placement.

## Границы

- Без полноценного строительного редактора.
- Без grid-based inventory.
- Без автоматической расстановки комнаты.
- Physical Storage Slots не заменяют stack/quantity Inventory из ТЗ 12.
- PlacementArea не является ownership container.
- Anchoring применяется только к явно поддерживающим его объектам.
