# RM06.1 — Физическое взаимодействие: Inspector-first компоненты, руки, Carry и Push

## Позиция в roadmap

Выполнить после R06 (Scanner / Registration / Terminal) и до R07 (Marker / Shelves).

Задача не заменяет R02, а доводит физическое взаимодействие до модели, пригодной для инструментов, оружия, двух рук, крупных Carry-объектов и будущих utility-механик.

## Цель

Разделить три независимых способа взаимодействия с физическими предметами:

- `CARRY` — крупный предмет перед игроком;
- `RIGHT_HAND` — предмет в правой руке;
- `LEFT_HAND` — предмет в левой руке;

и отдельно добавить механику `Push` для объектов вроде больших тележек.

Одновременно сделать компоненты Entity видимыми и настраиваемыми из Inspector, а не скрывать статическую конфигурацию в `define_components()`.

## Inspector-first authoring компонентов

Для scene-authored Entity основным способом задания компонентов является `component_resources` в сцене, как у Player и Box.

Требования:

- все статические и сериализуемые Components должны быть subresource/resource сцены и быть видны в Inspector;
- существующие `define_components()` необходимо проверить и перенести из кода в сцену там, где данные могут быть сериализованы;
- если Entity требует runtime-данные конкретного экземпляра, в `define_components()` остается только минимальная динамическая часть;
- допустимое исключение — данные, которые действительно нельзя корректно сериализовать/восстановить из сцены, например специфическая runtime-ссылка на Node; прямые ссылки на Node в Component не рекомендуются;
- не создавать один и тот же Component одновременно через `component_resources` и `define_components()`;
- InteractionAction/definitions, которые являются Resource и сериализуются, также предпочтительно настраивать из сцены.

Если часть `define_components()` остается, причина должна быть очевидна из кода и относиться к runtime-данным, а не к удобству программиста.

## Slot-based holding

Авторитет владения остается relationship, а не поле на holder.

`C_HeldBy` или эквивалентная relation должна хранить выбранный runtime-slot:

- `CARRY`;
- `RIGHT_HAND`;
- `LEFT_HAND`.

Требования:

- один физический объект не может одновременно принадлежать нескольким holder;
- один slot holder не может содержать два объекта;
- holder может одновременно иметь до трех объектов: один Carry + по одному в каждой руке;
- объект в левой/правой руке не блокирует поднятие Carry-объекта;
- Carry-объект не блокирует использование свободной руки;
- reverse index на holder является только derived cache и должен быть раздельным по slot, а не одним `held_object`;
- выбранная рука не должна быть жестко зашита в тип предмета: hand-item объявляет допустимые hand slots, а конкретный `LEFT_HAND/RIGHT_HAND` выбирается при pickup;
- anchor удержания определяется runtime-slot relationship, а не только конфигурацией предмета.

`C_CarryLoad` по умолчанию относится к `CARRY`. Предметы в руках не должны автоматически занимать Carry capacity или запрещать поднятие коробки.

## Управление руками

По умолчанию:

- primary hand = правая;
- secondary hand = левая;
- LMB использует предмет в правой руке;
- RMB использует предмет в левой руке;
- Alt + LMB бросает предмет из правой руки;
- Alt + RMB бросает предмет из левой руки.

Нужна опция `swap_hand_controls` (точное место хранения определить в реализации), которая меняет primary/secondary hand mapping. Физические слоты при этом остаются `LEFT_HAND/RIGHT_HAND`; меняется только управление и UI prompts.

### Pickup / replace hand-item

Для стандартного mapping:

| Состояние рук | E | F |
| --- | --- | --- |
| Обе свободны | взять hand-item в правую руку | отдельная замена не требуется |
| Одна занята | взять target в свободную руку | заменить предмет в занятой руке |
| Обе заняты | заменить предмет в правой руке | заменить предмет в левой руке |

При `swap_hand_controls` primary/secondary роли в этой таблице меняются местами.

Правила относятся к предметам, допускающим hand slots. Carry-only target использует независимый Carry slot и не должен отклоняться только потому, что занята одна или обе руки.

Взятие Carry обьекта (Заполнение Carrt Slot) должны временно скрыть руки, что бы не было конфликта с управлением на LMB/RMB.

Совобождение Carry slot возвращает руки на прежнее место.

Replacement должен сначала полностью провалидировать target/slot. Нельзя выбрасывать текущий предмет, а затем обнаруживать, что новый предмет взять невозможно.

## Drop

Добавить input action на клавишу `G`.

Короткое нажатие сбрасывает ровно один предмет — первый существующий по приоритету:

1. `CARRY`;
2. `LEFT_HAND`;
3. `RIGHT_HAND`.

Повторные нажатия продолжают этот порядок.

Зажатие `G` резервируется под будущее контекстное колесо. В RM06.1 достаточно placeholder-состояния/сигнала/UI без полноценного radial menu. Порог long-press должен быть конфигурируемым; срабатывание long-press не должно одновременно выполнять short-drop.

## Rotation policy носимых объектов

У носимого объекта должны быть data-driven настройки:

- разрешено ли ручное вращение вообще;
- ограничение осей вращения;
- сбрасывать ли ориентацию при pickup.

Минимально требуется режим свободного вращения и режим `Y_ONLY` для корзин/ведер. Архитектура не должна мешать позже добавить другие axis constraints.

Для Scanner, pistol и аналогичных tool/weapon можно полностью выключить manual rotation. Если rotation запрещен, action/prompt вращения не должен предлагаться и input не должен менять rotation offset.

Опция `reset_rotation_on_pickup` означает: при взятии ориентация предмета приводится к исходной ориентации относительно выбранного anchor/slot вместо сохранения случайного world rotation. Для предметов без этой опции текущая относительная ориентация сохраняется.


LMB/RMB Carry slot имеет приоритет выше чем над LMB/RMB hand-use, если он занят. LMB/RMB hand-use имеют приоритет над generic rotate. Rotation должен идти через общий interaction/action resolver и не может одновременно использовать ту же кнопку, которая уже использовала предмет в руке. Финальный binding вращения должен быть отражен в `docs/controls.md`.


## Push

Тележки и подобные крупные объекты реализовать отдельно от `C_Grabbable`.

Рекомендуемая граница — отдельный `C_Pushable` + `S_Push`/relation состояния push, но точные имена не являются обязательными.

Контракт:

- Pushable не занимает Carry/hand slot и не получает `C_HeldBy`;
- взаимодействие начинается через общий contextual interaction resolver;
- во время активного push/focus объект находится только перед игроком: механика не должна превращаться в pulling сзади;
- движение вперед толкает объект с фиксированной, data-driven скоростью;
- поворот влево/вправо вращает объект с фиксированной, data-driven angular speed;
- движение назад не тянет тележку на себя;
- столкновения с миром и другими телами остаются физическими;
- не телепортировать Transform ради удержания траектории;
- потеря валидного focus/дистанции/Entity должна безопасно завершать push-state.

Цель — получить предсказуемое управление большой тележкой независимо от чувствительности мыши и случайной скорости вращения RigidBody.

## Миграция существующих Entity

В рамках задачи проверить как минимум существующие project-owned Entity со своими `define_components()`, включая Scanner, Package и interaction/gameplay props.

Инвариантные Components перенести в `.tscn`. Runtime identity/state, который формируется из spawn-specific данных и действительно не может быть authored в сцене, оставить минимальным исключением.

## Критерии готовности

- Components обычных scene-authored Entity видны и редактируются в Inspector через `component_resources`.
- Scanner/другой hand-item можно положить в любую разрешенную свободную руку; выбранный slot хранится в relationship.
- Предмет в руке не мешает одновременно нести Carry-коробку.
- E/F корректно выбирают свободную руку или replacement по правилам выше.
- LMB/RMB используют соответствующие руки; switch меняет mapping без перестановки физических anchors.
- G дропает Carry → Left → Right по одному объекту; long-press дает placeholder будущего wheel.
- Alt + LMB/RMB бросает предмет из соответствующей mapped hand.
- Предмет с запрещенным rotation не вращается; Y-only не получает X/Z rotation; reset-on-pickup возвращает authored orientation.
- Pushable cart толкается только перед игроком с фиксированными скоростями движения/поворота и не использует Grab contract.
- Старые Carry/throw/release/physics invariants не ломаются.

## Границы

- Без полноценного radial/context wheel — только placeholder long-press.
- Без полноценной системы оружия; RM06.1 предоставляет hand/use/throw contract.
- Без Inventory ownership — это отдельная roadmap-задача.
- Push не должен превращаться в универсальную vehicle system.
- Addons/GECS остаются read-only.
