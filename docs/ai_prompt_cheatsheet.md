# Шпаргалка: Prompt → Plan → Goal

Обычно достаточно дать агенту цель, симптом/контракт и стартовый файл, если он известен. Не нужно перечислять все проектные документы.

## Маленький баг

```text
Исправь <симптом>.

Ошибка:
<короткий лог>

Начни с:
<файл / класс, если известен>

Не делай несвязанный refactor.
```

Для локального исправления отдельный task-файл не нужен.

## Обычная задача

```text
Реализуй <результат>.

Ограничения:
- ...
- ...

Начни с <файл/подсистема>, если известно.
Сначала составь Plan, затем после проверки плана выполняй по Goal.
```

Plan отвечает за маршрут выполнения. Goal фиксирует, что должно быть истинно в конце и как проверить завершение.

## Большая / межсессионная Feature

Если работа должна пережить текущий thread/session, укажи или создай один durable task:

```text
Продолжай agent_tasks/R35_<name>.md.
Используй его только как durable checkpoint; текущий execution веди через Plan + Goal.
```

Не создавать параллельно `CURRENT_WORK`, queue/status index или отдельный history-файл.

## Экономия контекста

- одна конкретная цель за раз;
- точный путь/символ лучше «изучи весь проект»;
- не просить заранее читать roadmap, architecture и все skills;
- MCP использовать для live scene/editor/runtime context, когда это реально помогает;
- не выгружать весь SceneTree/log без необходимости;
- не запускать broad tests после каждой мелкой правки;
- для отдельного review достаточно попросить focused review текущего diff.

## Параллельный review: пилот PVZ

Только для PVZ. Подробности: [Parallel review workflow](parallel_review_workflow.md).
Для стандартного сценария достаточно первого промпта — повторять всю
документацию или называть каждый skill не требуется.

### 1. Feature с параллельным review (основной шаблон)

```text
Реализуй [название функции] в PVZ. Начни с [конкретный файл/сцена].
Соблюдай текущую GECS архитектуру и Code Style.

После законченного логического checkpoint сделай отдельный коммит,
запусти read-only reviewer параллельно по точным BASE_SHA и TARGET_SHA.
Пока идёт ревью, продолжай только независимые подзадачи.
Когда отзыв вернётся, выполни triage, исправь принятые P0/P1/P2.
Не объявляй milestone DONE с REVIEW_PENDING или BLOCKED.
Запускай только релевантные локальные Godot/GUT/validator проверки.
Визуал и gameplay feel проверю сам.
```

### 2. Рефакторинг большой подсистемы

```text
Продолжай agent_tasks/refactoring_v2/[номер_задачи].md до acceptance.
Соблюдай GECS ownership, единственного state writer и контракт сцен/UID.
Раздели работу на отдельные законченные коммиты.

Для каждого существенного checkpoint отправляй reviewer
BASE_SHA..TARGET_SHA, не давай ему редактировать код или задачи.
Пока он занят, делай только не зависящую от результата работу.
Все findings записывай в существующую задачу, дедуплицируй по контракту.
После двух неуспешных целевых fix/re-review циклов останови эту
часть как BLOCKED, а не запускай бесконечные исправления.
```

### 3. Безопасный маленький Fix (Light)

```text
Исправь [симптом] в [файл]. Не меняй API и соседние подсистемы.
Выполни локальные проверки и краткий self-review.
Отдельного reviewer не запускай, если не затронуты
authority/save/GECS ownership/physics/lifecycle.
```

### 4. Возобновление после прерванного Codex сеанса

```text
Продолжай agent_tasks/[task].md.
Проверь последний checkpoint и его REVIEW_PENDING на полных SHA.
Сверь замечания с текущим HEAD, объединяй дубли и восстанови
статус каждой принятой ошибки. Не запускай второй reviewer,
если предыдущий ещё работает; если его результат недоступен,
назначь новый review конкретного SHA или отметь NOT_RUN.
```

### 5. Отдельный независимый review

```text
Проверь read-only коммиты BASE_SHA=[полный SHA] и
TARGET_SHA=[полный SHA]. Используй только git diff/git show
на этих ревизиях, без запуска Godot и правок файлов.
Проверь GECS roles, authority, нативные сцены и Code Style.
Верни R1.. с приоритетом, доказательством и минимальным исправлением.
Main разберёт findings и внесёт решение в текущую задачу.
```

### 6. Сравнение последовательного и параллельного режима

```text
Для 2–3 сопоставимых по сложности checkpoints фиксируй
end-to-end время, overlap review, токены (если доступны),
долю подтверждённых/ложных findings и число fix rounds.
Один checkpoint проверь серийно, следующий сопоставимый —
параллельно. Не запускай отдельные live evals для эксперимента.
Если метрики недоступны, пиши NOT_MEASURED, а не 0.
```
